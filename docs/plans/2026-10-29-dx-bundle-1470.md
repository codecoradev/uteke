## 2. (a) Front-matter on `doc export`

`doc export` already emits Markdown. Add `--front-matter` (default off, so existing output is byte-identical) that prepends

```
---
slug: <slug>
title: <title>
tags: [..]
parent: <parent slug or empty>
---
```

so a vault import keeps the hierarchy. Test: export with and without the flag; the body is identical and the front-matter parses as YAML; a round trip through `doc import` (if it reads front-matter, otherwise a note in the docs). One PR, no schema change.

## 3. (b) Read-only viewer

Proposal: `uteke view [--port N]` starts a small server bound to `127.0.0.1` only, serving one static page (no build step, no framework: a single HTML file with the JSON it needs fetched from existing read routes) that lists memories, namespaces, room stats and health. Read-only by construction: it uses a read-only token and calls only routes the registry already marks as reads (`api_registry.rs` has the `writes` flag), so a write route cannot be reached from it. No auth surface by default (loopback only); a non-loopback bind is refused unless the existing server auth token is set.

Alternative considered: a `/ui` route on `uteke-serve`. Rejected as the first step because it widens the surface of a process that may be exposed; a separate loopback command does not.

## 4. (c) Session timeline

Needs the `observations` table from #1466 (`session_id`, `seq`, `role`, `captured_at`). The view is a page (in the viewer) that lists a session's events in `seq` order and links each stored memory back to the session that produced it (`source = "observation:<session_id>"`). Not started until #1466 step 1 lands.
