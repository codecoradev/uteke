# Raw observation capture with deferred extraction (#1466)

Status: **design for agreement, no code yet.**

## 1. Where we are

- `uteke import --extract` runs an LLM per session (`crates/uteke-core/src/extraction.rs`: `Extractor::extract(text)` returns up to `max_facts` facts). Measured about 12.6 s per session. Fine for a backfill, far too slow for always-on capture, so sessions that are not imported by hand are lost.
- The server already runs background threads on an interval (`auto_lifecycle`, `auto_dream` in `crates/uteke-server/src/main.rs`) that take the store lock and skip a cycle when it is busy. The deferred extraction job can follow the same pattern.
- Stored memories go through the shared write tail (`commit_memory`, #1514) and the privacy filter (#1464).

## 2. Goal

Split capture (hot path, no LLM, about 0 ms) from extraction (cold path, scheduled, budgeted, resumable).

## 3. Design

### 3.1 Storage (schema v23, forward-only)

```
observations(
  id            TEXT PRIMARY KEY,      -- uuid v7
  session_id    TEXT NOT NULL,         -- caller-supplied
  seq           INTEGER NOT NULL,      -- order inside the session
  role          TEXT NOT NULL,         -- user | assistant | tool
  content       TEXT NOT NULL,         -- after the privacy filter
  content_hash  TEXT NOT NULL UNIQUE,  -- sha256(session_id, seq, role, content)
  source        TEXT,                  -- agent / machine
  captured_at   TEXT NOT NULL,
  status        TEXT NOT NULL DEFAULT 'pending'   -- pending | extracting | done | failed
)
extraction_runs(id, started_at, finished_at, sessions_done, facts_stored, error)
```

`UNIQUE(content_hash)` makes a repeated capture of the same turn a no-op (`INSERT OR IGNORE`), which is the dedup the issue asks for. The migration is additive; nothing existing changes.

### 3.2 Capture (hot path)

`uteke capture --session <id> --role <r> [--source <s>]` reads the turn from stdin and appends one row. The privacy filter runs here, so a secret never sits in the queue in clear text (the queue is not exempt from #1464). No embedder, no network, one SQLite insert: the target is p95 below 50 ms per session end. Also exposed as `POST /capture` (LAB) and an MCP tool, all through one core function.

### 3.3 Extraction (cold path)

`uteke extract-queue run [--budget N]` (and an optional server thread) takes up to N pending sessions, joins their turns in `seq` order, calls the configured `Extractor` (model, base URL and key from the existing `[extraction]` section, unchanged), and stores the facts through `commit_memory` with `source = "observation:<session_id>"` and the session id in metadata. Per session:

- mark `extracting` before the call, `done` (or back to `pending`, or `failed` after K attempts) after it, in one transaction with the stored facts, so a crash re-queues the session instead of losing or duplicating it;
- on HTTP 429 or a provider error stop the run and back off (the interval doubles up to a cap); never loop on a rate limit;
- `--budget` bounds LLM calls per run; progress is visible as counts (pending / extracting / done / failed) from `uteke extract-queue status` and `GET /capture/status`.

### 3.4 Config (`[capture]`, global file only)

`enabled`, `interval_minutes`, `budget_per_run`, `retention_days` (done observations older than this are deleted; raw transcripts should not live forever). Like `[privacy]`, the section is read from the global file only: a cloned repository must not be able to turn capture on or point it elsewhere.

### 3.5 Contract

All new routes and tools are LAB (no cloud port promised). The new table adds no CORE behaviour. If cloud later wants the same, it is a separate contract issue.

## 4. Acceptance (from the issue) and how each is tested

| Criterion | Test |
|---|---|
| Capture p95 below 50 ms, zero LLM calls | bench on the Modal harness (the perf baseline script) with a counting extractor that must record 0 calls |
| Hash dedup, re-capture is a no-op | capture the same turn twice: one row |
| Extraction resumable, budgeted, progress visible | fake extractor that fails the Nth call: restart, the session is re-queued once, counts add up |
| Config: interval, budget, enable/disable | config tests, including that a project file cannot set `[capture]` |
| 429 backoff | fake extractor returning 429: the run stops, the interval grows |

## 5. Sequencing

1. Schema v23 + `capture` core function + CLI (no server yet). Smallest useful slice; unblocks #1465.
2. `extract-queue run/status` with the fake extractor tests.
3. Server thread and `[capture]` config.
4. HTTP/MCP surfaces.

## 6. Open questions (owner)

- Retention default (proposal: 30 days after `done`).
- Do tool-call results get captured, or only user/assistant turns? (They are large and noisy; proposal: summaries only, as the issue says "tool summaries".)
- Should extraction batch several sessions into one LLM call to cut cost, or stay one session per call (simpler, resumable)? Proposal: one per call.
