# `uteke connect <agent>`: lifecycle hook adapters (#1465)

Status: **design for agreement, no code yet.** Depends on #1466 for the capture side (see "Sequencing").

## 1. Where we are

- `uteke init <agent>` already exists for `pi`, `claude`, `cursor`, `opencode` and `hermes` (`crates/uteke-cli/src/init.rs`), with a `--memory-provider` variant. It is a one-shot setup, not an idempotent install/uninstall pair, and it does not record what it wrote.
- `uteke hook <shell>` prints a shell snippet that activates a project store on `cd`. It is unrelated to agent lifecycle hooks (same word, different thing).
- Capture and recall hooks that work in the fleet today are machine-local scripts outside the product (hook path about 238 ms against about 315 ms for the MCP call). A new machine has no supported way to get them, and a hook that points at a path that moved dies silently.

## 2. Goal

`uteke connect <agent>` installs capture and recall hooks for an agent app; `uteke disconnect <agent>` removes exactly what `connect` installed. First targets: Claude Code, Cursor, Codex, Pi, Hermes (the ones in the issue).

## 3. Design

### 3.1 Hooks call the product, not a copied script

A hook entry runs `uteke hook-run <event>` (a hidden subcommand), resolved through `PATH` at run time, not an absolute path baked into a config file. The subcommand reads the agent's event payload from stdin and does the work (recall: print context; capture: enqueue an observation, see #1466). Consequences:

- there is no script to go stale; upgrading the binary upgrades every hook;
- the "silent hook death from a stale path" failure mode disappears: no path is baked in;
- the agent is never blocked by a missing binary. The command the adapter writes is not the bare `uteke hook-run <event>` (a missing binary would make the shell return 127 before any uteke code runs) but a guarded form, `sh -c 'command -v uteke >/dev/null 2>&1 && uteke hook-run <event> || true'`, and the equivalent for the agent's shell on Windows (PowerShell: `if (Get-Command uteke -ErrorAction SilentlyContinue) { uteke hook-run <event> }; exit 0`). Inside `hook-run`, any error is logged and the exit code is 0. Each adapter test asserts the exit code with `uteke` absent from `PATH`;
- the hook command string is identical on every machine, so an idempotency check is a string comparison.

### 3.2 Ownership record

`connect` writes a manifest `~/.codecora/uteke/connect/<agent>.json`: the config file touched, the exact entries added (verbatim JSON/TOML fragments) and the uteke version. `disconnect` removes only entries that still match the manifest byte for byte; an entry the user edited is left alone and reported. A re-run replaces only manifest entries. User entries are never reordered or rewritten (the merge preserves unknown keys and, where the format allows, comments).

### 3.3 Per-agent adapter

One small trait, one implementation per agent: `config_path()`, `render_entries()`, `merge(existing) -> merged`, `unmerge(existing, manifest) -> remaining`. The file formats and event names are **not** assumed here: each adapter's first task is to read that agent's current hook documentation and write the fixture the tests use. (Claude Code keeps hooks in `settings.json` under `hooks`; the others must be checked.)

### 3.4 Upgrade refresh

Because hooks call `uteke hook-run`, nothing in the agent config changes on upgrade. `uteke upgrade` (and `uteke doctor`) only compares the manifest's recorded uteke version and the adapter's `render_entries()` output; if the rendered entries differ (a new event, a renamed flag), `doctor` says so and `uteke connect <agent>` refreshes them.

### 3.5 Safety

- `connect --dry-run` prints the diff and writes nothing; the real run backs the file up once (`<file>.uteke-bak`).
- No network, no LLM on the hook path.
- The hook never fails the agent: the guarded command above covers a missing binary, and `hook-run` logs any error to `~/.codecora/uteke/hook.log` and exits 0.

## 4. Acceptance (from the issue) and how each is tested

| Criterion | Test |
|---|---|
| `connect` idempotent | run twice on a fixture config: second run is a byte-identical no-op; user entries and unknown keys preserved |
| `disconnect` removes only what `connect` created | connect, add a user entry, disconnect: the user entry and every other key remain; the file otherwise equals the original |
| Refresh on upgrade | adapter output changes between two versions: `doctor` reports it, `connect` rewrites only manifest entries |
| Smoke test per agent | fixture config per agent in the repo; CI runs connect/disconnect on a temp `HOME` |
| Docs page per agent | `docs/integrations/<agent>.md` |

## 5. Sequencing

1. **#1466 first** (the `capture` path without an LLM). Until it exists a capture hook has nothing cheap to call. The recall hook can ship earlier.
2. Adapter trait, manifest and the Claude Code adapter (the best-understood target) with the full test set.
3. The other agents, one PR each.
