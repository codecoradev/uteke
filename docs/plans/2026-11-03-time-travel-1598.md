# Honest time travel (#1598)

Status: **implemented (unreleased).** The contract answer (uteke-cloud#458, Amendment 3 of `kontrak-core-cloud`, owner order 2026-11-03) allowed both CORE parts: history is the default for `at` on every surface (no `history` wire parameter; the CLI `--history` flag is a deprecated no-op alias, §5.2), and caller validity goes into the columns on `POST /remember`, `PUT /memory` and MCP, with the metadata copy kept for one release (§5.1, §7). Rooms follow the same rule. Cloud follows in its own PRs.

Source: Agent Memory Atlas findings 2 and 8 (re-checked against `develop` @ 63bcc1f on 2026-11-03).

## 1. Problem

Two gaps make `recall --at` and `list --at` less honest than they claim:

1. **Rows deprecated after the instant never come back.** Since #1086 (v0.17, schema v17) the documented rule is "a memory deprecated after `at` existed at `at`". The predicate implements it (`memory_existed_at`, `operations/time_travel.rs`), and `recall_at_time` asks `recall_inner` for deprecated rows too. But the candidates come from the vector index, and every real deprecation path removes the vector: `soft_forget` (`operations/forget.rs`), supersede (`edges.rs`), contradiction resolution. So the predicate never sees those rows. The #1086 regression test only exercised the predicate on a hand-built `Memory`, so the gap was never caught. `list --at` is worse: its SQL still says `deprecated = 0` (`memory/crud.rs`, `list_at_time`).
2. **A caller cannot say when a fact was true.** `valid_from` is always the write time (`operations/write.rs`, `remember_precomputed_detailed`) and `valid_until` is only written by deprecation. `POST /remember` accepts `valid_from`/`valid_until` but stores them as metadata keys, not in the columns the time-travel predicate reads (`remember_request.rs`, wire table). MCP and the CLI do not accept them at all.

## 2. What exists today

| Piece | OSS | uteke-cloud (`develop` @ 8e4e999) |
|---|---|---|
| `valid_from` / `valid_until` columns | yes (TEXT, RFC3339) | yes (TIMESTAMPTZ, migration 002) |
| Caller validity on `POST /remember` | accepted, stored in **metadata** only | same, deliberately (`http_memory.rs`: "OSS: metadata only, no column") |
| `deprecated_at` | yes (v17), set on every deprecate path | yes |
| Deprecation writes `valid_until = now` | yes | yes (`store/crud.rs`) |
| Deprecation removes the vector | yes (index) | n/a (Qdrant payload filter, see `docs/01-architecture.md`) |
| `at` on `POST /recall` | yes, CORE-documented | **not implemented**: `RecallBody` has no `at` and no `deny_unknown_fields`, so the key is silently ignored |
| Deprecated rows keep their embedding | yes, the SQLite `embedding` blob stays (that is how `promote` re-adds the vector) | n/a |

So there is no Cloud behaviour to match for `at`: Cloud ignores it. The precedent from #1595 ("match what Cloud ships") does not settle this one, and the rule falls back to the contract: additive is fine, a CORE result change needs a contract issue first.

## 3. Semantics (prior art)

Bitemporal models (SQL:2011 system-versioned plus application-time tables, XTDB, Datomic `as-of`) keep two independent axes:

- **transaction time**: when the store believed a row. Uteke: `created_at` .. `deprecated_at`.
- **valid time**: when the fact was true in the world. Uteke: `valid_from` .. `valid_until`.

A Datomic `as-of T` read is transaction time only; SQL:2011 `FOR SYSTEM_TIME AS OF` likewise, with `FOR PORTION OF` / `BUSINESS_TIME` for the valid axis. XTDB answers "valid at V, as known at T".

Uteke's `at` already uses both axes at a single instant: `created_at <= at < deprecated_at` **and** `valid_from <= at < valid_until`. That reads as "what did we believe, at `at`, was true at `at`", which is the useful default for an agent and is what #1086 documented. We keep that meaning. Two consequences:

- A caller-supplied `valid_from` earlier than the write time does not make a memory appear at an `at` before it was written: at that instant the store did not know it yet. That is correct for "what did we believe then".
- The question "what was true at V, as we know it now" is a different query (valid time only). It is a follow-up (`valid_at`, LAB, §8), not a change to `at`.

The only thing that conflates the axes today is that deprecation overwrites `valid_until` with the deprecation time. With caller validity that would destroy information (a fact that ended in January, deprecated in March, would look valid in February). So deprecation keeps an earlier caller `valid_until` (§5.1).

## 4. Options for the `--at` candidate set

| Option | What | Cost | Verdict |
|---|---|---|---|
| A. Keep deprecated vectors in the index | Stop removing vectors on deprecate; filter at recall | Index grows with every correction; every live recall pays for filtering deprecated hits; changes `verify`/`repair` invariants (index = live rows) | Rejected |
| B. Pure SQL scan + cosine over blobs for all rows | Ignore the index for `at` | O(N × dims) per query: 100k rows × 768 dims ≈ 300 MB of blobs read per recall | Rejected for large stores |
| C. **Union**: index candidates (live rows) + SQL over the deprecated rows that were deprecated after `at` | The index answers what it holds; the rows it lacks come from SQL, scored by cosine on their stored blob | O(D × dims) extra, D = rows deprecated after `at` and created before it. Bounded by the deprecated set, which `prune` caps at `deprecated_ttl_days` | **Chosen** |

Cost of C on a large store: the extra query uses `deprecated = 1` plus the time bounds; D is usually a small fraction of N (corrections, not writes). Brute-force cosine is ~1 µs per 768-dim row, so even D = 10 000 adds ~10 ms plus blob reads. Rows without an embedding (FTS-only) are skipped; the time-travel path has always been vector-only.

**Do deprecated rows keep a vector?** In SQLite, yes: the blob stays until `prune` deletes the row. In the ANN index, no, and C does not need them there. History is therefore queryable for exactly as long as the row exists, i.e. up to `deprecated_ttl_days` (0 = forever). The audit timeline (#1280) outlives the row; the row is what `--at` needs.

## 5. Design

### 5.1 Caller-supplied validity (additive)

- Core: `Uteke::set_validity(id, valid_from, valid_until)`. Each side is optional (`None` keeps the stored value). Validated: the resulting `valid_from < valid_until`; refused on a deprecated memory (its `valid_until` is deprecation bookkeeping, use `promote` first). Values are stored as UTC RFC3339 like every other timestamp.
- Core: `RememberRequest` carries an optional typed validity that `run_remember` applies after the write, like `source`/`author` (same failure policy: the memory stays, the failure is a warning). `RememberRequest::decode` does **not** fill it: the HTTP wire fields keep their metadata behaviour (§7).
- CLI: `uteke remember --valid-from/--valid-until` and `uteke update --valid-from/--valid-until` (RFC3339). Validated before any write. Via a running server the remember falls back to the local store, as other flags the HTTP body cannot carry do.
- Deprecation keeps an earlier caller `valid_until`: every deprecate statement becomes `valid_until = CASE WHEN valid_until IS NOT NULL AND valid_until < now THEN valid_until ELSE now END`. Every row that exists today has `valid_until IS NULL` while live, so their deprecation is unchanged.
- Restore (`promote`, supersession undo) is unchanged: it clears `valid_until`. A caller `valid_until` is therefore lost on restore; set it again with `update --valid-until`. Telling a caller value from deprecation bookkeeping on restore would need a marker column, and legacy v17-backfilled rows make a timestamp comparison unsafe.
- Defaults unchanged: no flag, no change in stored values.

### 5.2 History mode for `--at` (opt-in)

- Core: `recall_at_time_history(...)` = today's `recall_at_time` candidates **plus** option C's SQL candidates, merged by score, then the same predicate and truncation. Score for a SQL candidate = cosine similarity of the query embedding and the stored blob, clamped to [0, 1], with the same hot-tier boost the index path applies.
- Core: `list_at_time` gains a `history` flag: with it the SQL keeps a deprecated row when `deprecated_at IS NULL OR deprecated_at > at` (the predicate's rule) instead of `deprecated = 0`.
- CLI: `uteke recall --at T --history`, `uteke list --at T --history`. `--history` without `--at` is an error. Via a running server the command falls back to the local store, like other flags HTTP cannot carry.
- No HTTP or MCP surface in this step, so no CORE result changes. The default `at` stays exactly as it is.

### 5.3 Relation to the timeline (#1280) and consolidation

- **Timeline** is per memory and append-only: "what happened to X" (created, updated, deprecated, superseded, forgot). It survives `forget` and `prune`. `--at` is a store-wide snapshot: "what did we believe at T". They complement each other; `--at --history` stops at `prune`, the timeline does not. A future step could rebuild a pruned snapshot from timeline events, which is out of scope.
- **Updates are in place.** `--at` returns the memory's current content, not its content at T. Supersede (new row, old row deprecated with `deprecated_at`) is the versioned path, and history mode makes it visible: before the supersession `--at --history` returns the old row, after it the new one.
- **Consolidation** merges by superseding/deprecating the sources, so with history mode the pre-merge memories show at an `at` before the merge. Nothing in consolidation changes.
- **Tombstones (#1597)** block re-writing a rejected value; they do not hide history. A memory forgotten as `wrong` still shows at an `at` before the forget in history mode, which is the honest answer to "what did we believe then".

## 6. Testing

- End-to-end (keyword embedder, no ONNX): remember, `soft_forget` and supersede a memory, then `recall_at_time_history` at an instant before the deprecation returns it and at an instant after does not; plain `recall_at_time` is unchanged (still misses it).
- `list_at_time(history)`: same instants; `history = false` returns exactly today's rows.
- Validity: `set_validity` round trip, `from >= until` refused, deprecated refused; deprecation keeps an earlier caller `valid_until` and replaces a later one; CLI flags parse and refuse bad RFC3339 before writing.

## 7. CORE impact and the contract issue

Additive, no contract change: the core library API, the CLI flags, deprecation preserving a value only the new paths can write.

Needs the contract first (uteke-cloud#458, Gitea; Cloud tracking issue #369), not implemented here:

1. **Default `at` includes rows deprecated after `at`** on `POST /recall`, `/list`, `/room/recall` and the MCP tools, i.e. history mode becomes the default. This is the meaning #1086 documented, but it changes results for existing callers, and Cloud would have to implement `at` at all.
2. **`POST /remember` `valid_from`/`valid_until` go into the columns** (and are validated), not only into metadata. Cloud stores them in metadata on purpose today. Accepting them on MCP `uteke_remember` and `POST /update` follows from the same decision.
3. **Cloud ignores `at` on `/recall` silently** (no `deny_unknown_fields`). That is drift on a CORE parameter regardless of 1 and 2.
