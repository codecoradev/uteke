# Unified Surfaces (#1439) and Namespace Deprecation (#1427) Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Every operation has one behaviour, owned by uteke-core. HTTP, MCP and CLI differ only in transport: auth, argument parsing and output format. This matches how uteke-cloud already serves MCP, by running each tool through its REST router.

**Architecture:** The typed request modules from #1343 (`recall_request.rs`, `list_request.rs`, `remember_request.rs`, `forget_request.rs`) become the single deep module per operation. Their `Policy::HTTP` / `Policy::MCP` constants are collapsed into one behaviour, and then the `*Policy` structs are deleted. The CLI runs the same `decode` before it picks a transport (server or local store). Namespace-related disagreements are not unified here: #1427 phase 4 (single-namespace mode) removes them.

**Tech Stack:** Rust workspace (uteke-core, uteke-server on tiny_http, uteke-mcp JSON-RPC, uteke-cli on clap). Tests use `Uteke::open_with_backend(":memory:", None)` (no ONNX in CI). Benchmarks use the Python harness in `benchmarks/longmemeval/scripts/`.

Decisions come from the grilling session of 2026-10-13 (Q1–Q20) and are recorded on [codecoradev/uteke#1439](https://github.com/codecoradev/uteke/issues/1439#issuecomment-6136926825).

## Phase 1, PR A: read-only gate for MCP tools over HTTP

**Problem:** `POST /mcp` is registered `writes: true` (`crates/uteke-server/src/api_registry.rs:870-877`).
- A read-only token cannot call any MCP tool, not even recall.
- Once `/mcp` is opened, nothing inside MCP is gated: `handle_jsonrpc` (`crates/uteke-mcp/src/lib.rs:68`) has no notion of the caller.

uteke-cloud refuses destructive tools for read-only keys. This PR does the same.

**Design:**
- Add `Access { Full, ReadOnly }` and `handle_jsonrpc_as(uteke, raw, access)` in uteke-mcp. `handle_jsonrpc` keeps its signature and means `Full`, so stdio is unchanged.
- The allowlist is the MCP counterpart of the GET rows and non-writing POST rows in the registry.
- `/mcp` becomes `writes: false` and the per-tool gate does the work.
- Write tokens are unchanged. Read-only tokens gain read tools only.

## Phase 2: one behaviour per operation (after 0.21.0)

Each PR covers **one operation on all three surfaces**: HTTP, MCP, CLI via-server and CLI local. A surface is never left half-unified. Expand each into bite-sized TDD steps when it starts.

**Pre-condition:** the Appendix A contract issue has been posted on uteke-cloud.

**Common shape for C–F:**
1. Change the operation's `Policy::MCP` (and any HTTP field being changed) to the decided value. The existing side-by-side tests in `*_request.rs` flip from "pins the divergence" to "pins the one behaviour". Make those test diffs first (red), then the constants (green).
2. MCP: the `decode_*_args` function rejects unknown arguments with a message that lists the supported ones (cloud uses `-32602`; OSS returns its tool error). Build the known-key list from the tool's `inputSchema` properties, so the two cannot drift.
3. CLI local: `crates/uteke-cli/src/commands/<op>.rs` builds the core `*Input`, calls `decode`, and passes the decoded request to the same core call it makes today. The via-server path (`crates/uteke-cli/src/commands/server.rs`) sends the same decoded request. **Decode never selects a different core function.** In particular `recall` keeps `recall_unified` and its flags.
4. CHANGELOG `### Behavior Change` per surface.

### PR C: recall

- `limit` cap **100** everywhere; a CLI value above 100 is clamped with a stderr warning.
- A blank query is rejected.

- MCP honours entity/category/enrich/at/after/before.
- `explain` + `search_type` follow the HTTP rule.
- An invalid `limit` is an error.
- `full_ids` stays MCP-only and moves to MCP output formatting.
